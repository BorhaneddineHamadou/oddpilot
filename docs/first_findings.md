# First findings — physcheck v0.1 over three public scenario corpora

**Date: 2026-07-20 · physcheck 0.1.0, layers L0–L1, full shipped catalog (92 YAML rules + 8
structural plugin rules).**

Command: `physcheck lint <corpus> --format json --severity info --fail-on never`.

## Corpora

| Corpus | Source / revision | .xosc files | Concrete scenarios¹ |
|---|---|---|---|
| CARLA ScenarioRunner examples | `carla-simulator/scenario_runner` `srunner/examples` (local checkout) | 15 | 9 |
| esmini resources | `esmini/esmini` @ `77028d8` (2026-07-17), `resources/xosc` | 79 | 68 |
| ASAM OSC-ALKS-scenarios | `asam-oss/OSC-ALKS-scenarios` @ `b49dc1d` (2025-02-11) | 34 | 15 |

¹ Remaining files are catalogs and ParameterValueDistribution documents, which physcheck
recognizes and skips (reported as non-scenario documents).

## Headline result

| Corpus | Scenarios with ≥1 **error** | with ≥1 error or warning |
|---|---|---|
| CARLA ScenarioRunner | **8 / 9 (89%)** | 8 / 9 |
| esmini | 3 / 68 (4%) | 7 / 68 (10%) |
| ASAM ALKS | **0 / 15 (0%)** | 0 / 15 |

Two ends of the spectrum, exactly as the design brief predicts: a widely copied example
suite ships physically impossible attribute values in nearly every scenario, while the
regulatory ALKS corpus — which is CI-validated and encodes plausibility bounds *inside*
its scenarios as ValueConstraintGroups — comes out perfectly clean. The clean ALKS run
doubles as a false-positive check for the catalog: 33 info-level notices there are all
SCH-007 ("entity from unresolved catalog"), a documented v0.1 limitation, not findings
against the scenarios.

## What was found

### CARLA ScenarioRunner examples (the motivating case)

- **`maxAcceleration = 200 m/s² (~20 g)`** declared for *every* vehicle in every example
  (14 KIN-018 errors + 14 FRI-023 friction-circle errors + 12 KIN-019 warnings). This is
  a copy-pasted placeholder in the template all examples derive from — the exact class of
  defect that propagates into generated suites built on these templates.
- **Rain from a cloud-free sky** (3× PRE-012): `ChangingWeather.xosc` switches
  precipitation to rain at intensity 0.9 while `cloudState="free"` — definitionally
  impossible (WMO-No. 407).
- **The fog idiom** (9× ATM-001): `Fog visualRange="100000"` declared in every
  environment — a Fog element declaring 100 km visibility, the brief's "dense fog with
  unlimited visibility" pattern in its benign-but-sloppy form.
- **Sun at 75° elevation at 22:00** (SOL-007): the day→night weather change in
  `ChangingWeather.xosc` sets `dateTime` to 22:00 but keeps `elevation="1.31"` rad — a
  midnight sun below the polar circle.
- **Copy-pasted car bounding boxes on VRUs**: the crossing *pedestrian* and the
  *cyclist* both have a 4.5 × 2.1 × 1.8 m bounding box (ENT-010, ENT-011) — car
  dimensions on a pedestrian entity — plus a 10 m/s pedestrian (KIN-002) and a bicycle
  with 10 m/s² brakes, beyond the pitch-over limit (KIN-017).

### esmini resources

Mostly clean, with real catches:

- `cut-in_interactive.xosc`, `cut-in_sumo.xosc`, `acc-test.xosc`: `maxAcceleration` /
  `maxDeceleration` = **100 m/s²** placeholders (KIN-014 errors, KIN-018/019).
- `cut-in_environment.xosc`: the Fog-as-visibility idiom at 10 km (ATM-001 warnings) —
  interesting because this file is esmini's *showcase* for the OSC 1.3 Environment
  element.
- `straight_500m_pedestrian.xosc`: a pedestrian sustained at 8.0 m/s — flagged info
  (running) and at the exact boundary of the trained-sprinter warning.

### ASAM OSC-ALKS-scenarios

Zero findings. The corpus resolves everything through catalogs (v0.1 cannot check
catalog-defined vehicle attributes — SCH-007 notices), but its in-scenario values
(speeds ≤ 60 km/h with declared constraints, lateral velocities bounded by parameter
constraint groups) all pass. This corpus is the model of what the linter should *not*
flag.

## Reading of the results

1. **The defect class is real and concentrated in templates.** The single
   `maxAcceleration="200"` placeholder accounts for most errors in the ScenarioRunner
   corpus; every suite generated by instantiating these templates inherits it. Linting
   at authoring time (one `physcheck lint` in CI) removes it everywhere at once.
2. **Environment self-consistency defects (rain/cloud, sun/time) exist even in
   hand-written showcase files**, not just in generated scenarios — supporting the
   brief's claim that plausibility checking must be a first-class campaign step.
3. **A cited catalog can be strict without being noisy**: 0 errors and 0 warnings on the
   15 CI-validated ALKS scenarios, while flagging 89% of the CARLA examples.
4. **v0.1 blind spot**: corpora that push all entity definitions into catalogs (ALKS,
   most esmini files) currently escape entity-envelope rules. Catalog resolution is the
   highest-value L0 extension for v0.2 (tracked in decisions.md D12).

## Reproduction

```bash
git clone https://github.com/esmini/esmini            # resources/xosc
git clone https://github.com/asam-oss/OSC-ALKS-scenarios
git clone https://github.com/carla-simulator/scenario_runner
pip install -e physcheck/
physcheck lint esmini/resources/xosc --severity info --fail-on never --format json -o esmini.json
physcheck lint OSC-ALKS-scenarios     --severity info --fail-on never --format json -o alks.json
physcheck lint scenario_runner/srunner/examples --severity info --fail-on never --format json -o srunner.json
```

## Update: rescan with catalog resolution + version gating (same day)

After implementing catalog resolution (decisions D18), version gating (D19) and the
cross-environment monotonicity rule (D20), the same corpora were rescanned:

| Corpus | Scenarios with ≥1 error (before → after) |
|---|---|
| CARLA ScenarioRunner | 8/9 → **9/9** |
| esmini | 3/68 → 5/68 |
| ASAM ALKS | 0/15 → 0/15 (still no errors; now with real warnings) |

What resolving catalogs revealed — all previously invisible:

- **ScenarioRunner's `CatalogExample.xosc`** resolves to catalog vehicles with
  **zero-dimension bounding boxes** (SCH-112) and **mass = 0** (SCH-114) — now every
  example scenario has at least one error.
- **esmini's shipped `VehicleCatalog.xosc`** gives its *bus* a car-sized bounding box
  (4.5 × 1.8 × 1.5 m, a copy-paste default) with maxSpeed 70 m/s (252 km/h) — KIN-013
  ×14, KIN-015 ×14, KIN-020 ×14 across every scenario using catalog trucks/buses; its
  SUMO template vehicle is a 6.04 × 2.5 m "car" (ENT-002/003); and its *environment
  catalog* "winter" entry declares atmosphericPressure = 10 000 Pa, below the OSC
  schema range [80 000..120 000] (SCH-109 — a new **error** in the showcase
  environment file). Ego vehicles in `straight_500m*.xosc` declare maxDeceleration =
  30 m/s² (KIN-014 errors), and `routing-test.xosc` commands a 15 m/s² speed change
  (KIN-024).
- **ALKS** finally gets its entities judged: 22 KIN-019 warnings (catalog cars declare
  maxAcceleration = 10 m/s², ~1 g) and one 15.5 m bus (ENT-005) — still zero errors,
  preserving its role as the false-positive check.

The v0.1 blind spot quantified above is closed: catalog-defined entities no longer
escape the envelope rules.
